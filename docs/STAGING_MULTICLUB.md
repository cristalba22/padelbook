# Staging multiclub

Este entorno permite probar dos clubes durante varios días sin modificar el piloto publicado. La página de pruebas es [padelbook-staging.crisalbavideografo.workers.dev](https://padelbook-staging.crisalbavideografo.workers.dev). La API `padelbook-api-staging` usa la rama `codex/multisite-foundation` en Render Free, y el Worker `padelbook-staging` usa `wrangler.staging.jsonc`. El servicio gratuito puede suspenderse por inactividad: medir el primer arranque por separado de la respuesta con la API activa.

## Separación y credenciales

- Atlas: base `padelbook_multiclub_staging` en `Cluster0`; usuario `padelbook_staging` con privilegio `readWrite` **solo** sobre esa base y recurso restringido a ese clúster. La contraseña está en las variables privadas de Render. Para el alta inicial se usó una copia temporal local, ya eliminada. El clúster físico es compartido con el piloto: esto separa permisos y datos lógicos, pero no sustituye un clúster independiente.
- Render: ambiente `Staging multiclub`, servicio `padelbook-api-staging` en plan Free, rama del PR, `npm ci --omit=dev`, `npm run start:api`, healthcheck `/api/health`, auto deploy desactivado.
- Variables Render: `NODE_ENV=production`, `PADELBOOK_OPERATING_MODE=multiclub`, `PADELBOOK_DEMO_SEED=false`, `MONGODB_URI` del usuario restringido, `MONGODB_DB_NAME=padelbook_multiclub_staging`, `JWT_SECRET` y `API_PROXY_SECRET` aleatorios e independientes del piloto, `CLIENT_ORIGIN` y `PUBLIC_APP_ORIGIN` con el origen HTTPS exacto del Worker, `COOKIE_SAME_SITE=strict`.
- Cloudflare: Worker de staging con nombre distinto al publicado, `API_ORIGIN=https://padelbook-api-staging.onrender.com` y secreto `API_PROXY_SECRET` igual al de la API de staging. `PADELBOOK_STAGING=true` añade `X-Robots-Tag: noindex, nofollow, noarchive` a las respuestas públicas del staging. El Worker de producción conserva su configuración y sus secretos.
- Correo: sin dominio propio verificado de PadelBook, no configurar `RESEND_API_KEY` ni `PASSWORD_RESET_FROM` en staging. Las invitaciones y la recuperación reales quedan bloqueadas hasta verificar un remitente del producto. Nunca usar el dominio de Cerca Liceo como remitente permanente.

La lista de IP de Atlas ya permite `0.0.0.0/0` por la API existente. Staging **no añade** otra regla de red; el usuario restringido reduce el alcance de sus credenciales. Revisar la eliminación del acceso global cuando la infraestructura disponga de IP de salida fija o acceso privado, sin interrumpir la API del piloto.

## Alta controlada y prueba realizada

La base nueva se inicializó con `scripts/bootstrap-multiclub-staging.mjs`, que exige el usuario restringido `padelbook_staging` y un `--expected-host` explícito de Atlas, comprueba que ninguna colección tenga documentos, crea los datos en una transacción y verifica los índices de aislamiento. Recibe `--uri-file` y `--credentials-file` para que la URI no aparezca en el comando ni en el repositorio. Crea cuentas ficticias `@qa.invalid` con contraseñas aleatorias, dos organizaciones, tres sedes y una cancha con precios distintos por sede. El archivo de credenciales queda **fuera del repositorio**, bajo el perfil local del operador; no copiarlo a Git, Render ni documentación. El script no se puede repetir sobre una base que ya contiene datos.

La API quedó activa en `https://padelbook-api-staging.onrender.com/api/health`: `database=connected`, `mode=multiclub`, `writable=true`. La prueba `npm run qa:staging` se ejecutó contra esta API con cuatro cuentas y `STAGING_PROXY_SECRET_FILE` local. También se repitió a través del Worker público: el healthcheck respondió con la base conectada. Los propietarios solo pudieron acceder a su club; recepción pudo trabajar en Centro, pero recibió 403 en Norte y Villa Allende. El jugador reservó el mismo turno en tres sedes; un duplicado, dos reservas concurrentes y un bloqueo concurrente entre recepción y jugador devolvieron 409 para la operación perdedora. Los turnos y el bloqueo creados en la prueba se cancelaron o retiraron. Las reservas canceladas permanecen como auditoría.

El 9 de octubre de 2026 se ensayó además el frontend público en un viewport móvil de 390 × 844 px. Una cuenta de jugador eligió Club Sierras QA, sede Villa Allende, fecha futura y turno de 1 h 30; la confirmación mostró el importe de $37.500 y la reserva apareció en Mis turnos. Con la cuenta propietaria de Sierras, el panel solo mostró su club, encontró la reserva, la confirmó y actualizó el conteo y el saldo pendiente. La reserva de prueba se canceló y la agenda volvió a cero. En la fila cancelada se muestra el precio histórico y “Sin cobros registrados”, sin un saldo exigible. No se asentó un cobro simulado en la caja. Con la cuenta propietaria de Córdoba se verificó que solo aparece Club Córdoba QA y que su panel contiene Centro y Norte, sin Villa Allende. Capturas: `docs/screenshots/qa-staging-mobile-sierras-2026-10-09.png`, `docs/screenshots/qa-staging-admin-cancelado-2026-10-09.png` y `docs/screenshots/qa-staging-owner-cordoba-2026-10-09.png`.

Para repetir: definir `STAGING_ORIGIN` y `STAGING_EXPECTED_HOST` con el host exacto de staging, `STAGING_CREDENTIALS_FILE` con el archivo privado y, al probar la API Render directamente, `STAGING_PROXY_SECRET_FILE` con la clave temporal. Definir una fecha futura en `STAGING_SMOKE_DATE` para incluir escrituras; sin esa fecha el script solo lee. El script rechaza hosts de producción. El archivo de la clave proxy temporal debe eliminarse al finalizar. Nunca apuntar esta prueba a la base ni a la API del piloto.

Queda una prueba de aceptación en un teléfono real con el personal del club: reserva, confirmación por recepción, cancelación, caja con dinero realmente recibido y cambios de configuración en ambas sedes. Registrar tiempos con la API fría y activa, errores, capturas y versión del commit. El smoke automatizado y el navegador de escritorio en tamaño móvil no reemplazan esa prueba.

## Puerta de salida

Antes de llevar multiclub a producción: verificar restauración de un backup reciente en otra base; ensayar el cambio de versión y su reversión antes de admitir nuevas escrituras; confirmar aislamiento con dos operadores reales; verificar un dominio de correo de PadelBook y la entrega real; acordar con el club cómo se registran y concilian los cobros manuales. La seña online todavía no está implementada.
